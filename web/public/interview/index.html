01 · Engine

Rules engine

game.py · cards · melds · match

What it is

A pure-Python state machine for one round (RummyGame) and a 7-round match wrapper (match.py). It deals 162 physical cards (3 decks + 6 printed jokers), enforces every house rule (R1–R11), validates rummies, handles reveal of the original, the closed joker (CJ) and wild rank, forfeits, reshuffles and scoring, and appends an event for every transition so the UI can animate it.

Why it's built this way

  • Single source of truth for rules. The RL environment, the server and the puzzle generator all call the same engine, so the AI can never train on rules the website doesn't enforce.
  • Two id spaces. Physical card ids (0–161) for the UI and animation; card types (0–52) and count vectors for the solver and features, because three copies of 7♥ are interchangeable for strategy.
  • Reproducible. A round is fully determined by (seed, action list), which made bugs replayable and evaluations comparable.
  • Invariants asserted in tests: 162 cards conserved across zones, 13 cards between turns, locked cards never leave the hand, the CJ is never in a zone.

Top 10 interview questions

Q1Why model the game as an explicit state machine?
Each decision point (draw, discard/forfeit, reveal) is a state with its own legal actions. Making phases explicit means legality is a function of the state, the server can return 409 for out-of-phase requests, and the RL env only needs to ask “whose turn and what's legal”. Automatic transitions (win check, reshuffle, CJ flip) run in END_CHECKS without a player decision.
Q2Why separate physical card ids from card types?
The UI must animate a specific card (which 7♥ moved), but strategy only depends on how many of each type you hold. Types give a 53-long count vector that is cheap to hash, memoise and encode as features; physical ids keep the animation honest.
Q3How does the engine accept both RL actions and UI actions?
step() takes RL integers (0 closed draw, 1 open draw, 2–54 discard by type, 55 forfeit) and UI tuples like ("discard", card_id) or ("reveal", card_ids). Reveals are resolved by a per-player reveal policy (automatic for the AI and RL), or wait for an explicit UI action for the human (D-055).
Q4How is hidden information protected at the engine level?
get_state(pid) builds the acting player's information set only: own hand, revealed originals, discard history, cards the opponent picked from the open pile, and the CJ only after your own reveal. The draw-pile order and the opponent's closed cards never enter it, so features built from it cannot leak.
Q5What does the event log give you?
Every transition (deal, draw, discard, reveal, cj_flip, declare, reshuffle, round_end) is appended with a sequence number. The server streams the new events to the browser, which replays them as animations in order, then applies the final view, so the animation can never disagree with the state.
Q6How do you know the engine is correct?
~280 pytest tests: hand-made rule cases per rule id (R1–R11), seeded random-play invariant loops (thousands of rounds), and property tests that compare the fast solver against an exhaustive oracle built on the slow validators in melds.py.
Q7What edge cases were tricky?
A pre-original player taking the open card must reveal an original containing it that same turn, so some discards become illegal; the first-turn forfeit after a closed draw means discarding exactly the drawn card; a same-turn win before seeing the CJ only treats printed jokers as wild; and the 3/3/3/3 + 1 scoring rule for a loser added after user review.
Q8How is the reveal made unskippable?
A pending reveal at the end of a turn blocks every other action in the engine (D-056), not just in the UI. The front end shows a modal, but even a hand-crafted API call cannot skip it.
Q9How do variants (10-card, 7-card) fit in?
A Variant dataclass holds decks, jokers, hand size, win template, turn cap and penalty values. Everything else (solver slots, scoring, features) reads the template from it, so variants are configuration, not code branches.
Q10Why no torch in the engine package?
The engine is imported by the production server, which runs on 512 MB RAM. Keeping it NumPy-only made the deployed image small and let inference run without PyTorch at all.

02 · Engine

Arrangement solver

solver.py · patterns.py

What it is

Given a hand (count vector) and a context (locked original, wild rank, pre/post-original), finds the lowest-points arrangement into rummies that fits the 3/3/3/4 template, checks an exact-cover win, enumerates valid originals and evaluates every discard. It powers scoring, legality, the heuristic, the features and the coach.

Why it's built this way

  • Performance-critical: features need solve(hand − t) for every discard of every decision, so it must be ~milliseconds.
  • Pattern table: every valid rummy shape (natural-card multiset, wilds needed, size, kind) is precomputed once at import.
  • Memoised DFS: state = (remaining natural counts as bytes, wilds left, open slots). Branch on the first remaining card: leave it loose (pay its points) or put it in one of the patterns that contain it.
  • Template slots model “at most one 4-card rummy”; for scoring a 3-card rummy may fill the 4-slot (3/3/3/3 + 1), while a win still needs exact sizes.
  • Oracle-tested against a brute-force search over all groupings.

Top 10 interview questions

Q1Why not brute-force every partition of 14 cards?
The number of set partitions explodes and most aren't rummies. Branching only on the first remaining card, over precomputed patterns that contain it, plus memoising on the residual count vector, collapses identical sub-problems (three copies of a card are interchangeable).
Q2What is memoised and why bytes?
The key is (natural counts, wilds left, remaining slots). The counts are a 52-long small-int vector; converting to bytes makes it hashable and cheap to compare, so dict lookups dominate rather than recursion.
Q3How are wild cards handled?
Printed jokers and (post-original) wild-rank cards are pulled into a wild pool. Patterns declare how many wilds they need, and leftover wilds score 0. Wild-rank cards can also act as their natural selves, and a meld made only of pool cards is valid only if it contains a wild-rank card (≥1 natural rule, D-052).
Q4Why do jokers get used before wild-rank cards in the win search?
A pool-only rummy needs a wild-rank card to count as its natural card. Spending printed jokers first keeps wild-rank cards available for that case; an exchange argument shows this never loses a win, and the oracle tests confirm it (D-053).
Q5How does the template constraint work?
Remaining slot sizes (e.g. 3,3,4 after a 3-card original) travel through the recursion. Scoring takes the smallest slot at least the rummy's size, so a 3-card rummy may use the 4-slot; taking the exact size first is never worse because a bigger slot can hold anything a smaller one can.
Q6Why is winning a separate exact-cover search?
Scoring minimises points and may leave cards loose; a win needs every one of the 13 cards covered by exactly 3/3/3/4. A 0-point wild left out of rummies would make the scorer report 0 points without a win, so the two must be different searches (D-060b).
Q7How do you test a solver like this?
Random dense hands (few suits, few ranks, jokers) so rummies are common, then compare points and win/no-win against an exhaustive oracle that tries every group and every slot. Over a thousand random cases plus hand-made rule cases run in CI.
Q8What is discard_eval used for?
It returns the arrangement after removing each candidate discard: points left, loose-card count, whether it wins, whether an original survives. Those become feature block I, the heuristic's ranking, and the coach's reason tags.
Q9How do pre-original hands get scored for features?
They are solved “as if” the best available original were declared, plus original_outs, the number of unseen cards that would complete one. Without an original it returns an optimistic lower bound, which is fine for features but never used for real scoring (a pre-original loser always scores 80).
Q10What would you optimise next?
A lower-bound prune (remaining points minus coverable points), sharing the cache across the 14 discard evaluations of one decision, or numba on the inner loop. It was fast enough in practice (a full hint, including every discard evaluation and the value net, has a ~65 ms local median), so this wasn't needed.

03 · Engine

Observation encoder

features.py · 1,098 inputs

What it is

Turns a player's information set into a fixed 1,098-number vector for the networks, plus an Analysis object (solver facts, legal actions, outs) shared by the heuristic, the coach and the reward shaping.

Why it's built this way

  • Threshold encoding of counts (bits ≥1, ≥2, ≥3; jokers up to ≥6): 162 bits per card block, monotone and easy for an MLP.
  • Blocks: own hand, locked original, discard top, wild rank, dead cards, opponent's known cards, phase flags, drawn card, pile sizes.
  • Engineered solver features (block I, 6 rows × 53 types): points after each discard, in-best-arrangement, outs, discard-wins, loose cards after, original-remains. These give the network the combinatorics it can't learn cheaply.
  • FEATURE_VERSION is stored in every checkpoint and checked at load, so a model can never silently run on a changed encoding.

Top 10 interview questions

Q1Why engineer solver features instead of letting the network learn?
Whether a discard keeps a 3/3/3/4 cover is a hard combinatorial function of 14 cards. An imitation probe showed a raw-ish encoding agreed with the heuristic on only ~42% of discards; adding per-discard solver rows (points after, loose cards after, original remains) is what made imitation work (D-061, D-066).
Q2Why threshold rather than one-hot or raw counts?
With three copies per card, ‘≥1, ≥2, ≥3’ bits are monotone: holding two 7♥ turns on the first two bits. That shares statistical strength between counts and avoids a network having to learn that 3 > 2 from a scalar.
Q3How do you guarantee no hidden information leaks into the observation?
The encoder only reads the per-player state from get_state(pid), which is built from the information set (R11). API tests also assert the server never sends the AI's hand, the draw pile or the CJ early, and outs are computed from unseen copies (162 − own − dead − opponent-known), not from the real deck.
Q4What are ‘outs’ and how are they approximated?
Unseen copies of card types that would improve the hand: those that complete a rummy from two uncovered cards, plus unseen wilds when at least two natural cards are uncovered. Pre-original ‘original outs’ are exact: unseen cards that complete a natural original (D-058).
Q5Why version the features?
Any change to the encoding changes the meaning of every input weight. The version is saved with checkpoints and exported .npz files and asserted at load, so a mismatch fails loudly instead of producing a plausible but wrong policy.
Q6Why is the Analysis object shared?
The heuristic, reward shaping (Φ uses min points / original outs), the coach's tags and the features all need the same solver facts. Computing them once per decision keeps them consistent and avoids paying for the solver several times.
Q7How large is the vector and why does size matter?
1,098 floats. It sets the first-layer width (1,098 × 512 weights) and the replay buffer memory: 300k transitions store two observations each, which is why the buffer keeps them as float16 (halving RAM).
Q8How did the 3/3/3/3 rule change affect the encoder?
Block I values (points after a discard) changed for near-win hands. Rather than assume, the shipped DQN and value net were re-evaluated under the new rule: DQN 38.3% vs heuristic (up from 35.0%) and value ECE 0.021, so no retraining was needed.
Q9What features would you add next?
Opponent modelling (what suits/ranks they've picked or avoided over time), a discard-history recency window, and a ‘danger’ score for feeding the opponent, which the coach currently only approximates with an ‘AI may want it’ tag.
Q10Normalisation?
Scalars are scaled into [0,1] (points/80, outs/20, pile sizes/134, turn/100). RLCard's estimator also starts with a BatchNorm layer, which the NumPy export reproduces as an affine transform.

04 · Engine

Heuristic agent

agents/heuristic.py

What it is

A hand-written expert: draws the open card only when it completes an original, a win, or saves ≥ 3 points; discards by minimising a score (points after + 1.5·loose cards − 0.8·outs + small tie-breaks, never a wild); forfeits only with no original, ≤ 2 original outs and no joker. It is the curriculum opponent, the demonstrator for imitation learning, the Easy base (with ε-random moves) and, in the end, the Hard AI.

Why it's built this way

  • Strong baseline first. In a 3-day sprint a solver-backed heuristic gives a guaranteed competent opponent, and an RL agent needs something to beat.
  • Demonstrator: 60k heuristic transitions warm-start the replay buffer and drive DQfD pretraining.
  • Fixes found by self-play stats: never take back a card you discarded (breaks pick-up/throw-back loops), always play a winning discard, penalise loose cards because a win needs an exact cover (D-060).
  • Hard = heuristic because it was measurably the strongest player (D-034, D-096).

Top 10 interview questions

Q1Why does the heuristic penalise loose cards, not just points?
Wild cards score 0, so a hand can show 0 points while still having loose cards and not being a win. Since a win requires every card in a rummy, the count of loose cards is a better ‘distance to win’ than points alone.
Q2What is the discard score exactly?
Post-original: points_after + 1.5·loose_after − 0.8·outs_after + 0.05·card_points (+100 if wild); a winning discard is always chosen first. Pre-original it adds a penalty of 15 if no original remains after the discard and weights points less (0.3×).
Q3Why never take back your own discard?
Two heuristics can loop forever: one throws X, the other takes it, throws it back. The rule removes the cycle and slightly improves strength; it was found by looking at long self-play rounds.
Q4How does the reveal choice work?
Among valid originals, pick the one that maximises expected −min_points over the possible wild ranks weighted by unseen counts; ties keep cards that belong to more candidate rummies. A 3-card reveal is weakly dominant because it can be extended later.
Q5How is Easy built from it?
Easy = heuristic with ε = 0.35: 35% of the time a uniformly random legal move (never forfeiting). Over 4,000 rounds a 30% version wins ~30% against the full heuristic, giving a clear, calibrated step down.
Q6Why didn't the DQN beat it?
The heuristic sits on top of an exact solver, so its discards already exploit the hard combinatorics. The remaining edge (opponent reading, timing) needs long-horizon credit assignment under hidden information, which DQN with ~100k rounds of self-play didn't find; RL fine-tuning drifted instead (see DQN).
Q7Is it fair to call the product an RL project if Hard is a heuristic?
Yes, if you're honest about it: the RL pipeline produced the Medium opponent, the coach's Q-value rankings and the value network, and the evaluation decided objectively that the heuristic is stronger. Shipping the weaker model as ‘Hard’ would have been misleading.
Q8How does the forfeit rule compare to an expected-value rule?
Forfeit costs 40; losing without an original costs 80. The heuristic approximates ‘P(no original by round end) is high’ with no original, ≤ 2 original outs and no joker. A value-net-based rule (forfeit if predicted score difference < −0.5) was specified but the simple rule was kept.
Q9How fast is it?
One solver call per candidate discard (≤ 14) per decision, memoised; in practice milliseconds per move locally, so it was also cheap enough to generate 60k demonstrations and 3,000-round statistics.
Q10How did it help generate the Learn content?
‘Best discard’ puzzles come from heuristic self-play positions where the best discard beats the runner-up by ≥ 2 score points (one clear answer); strategy-note numbers come from 3,000 heuristic self-play rounds.

05 · Engine

Hybrid policy

agents/hybrid.py

What it is

The DQN chooses among the heuristic's top-3 discards (and forfeit when legal); a winning discard is always taken; draw decisions come from the DQN. It scored 48.2% against the heuristic, versus 38.3% for the DQN alone. It powers the coach's top suggestion.

Why it's built this way

  • Constrained action space: the heuristic prunes obviously bad discards, the network breaks ties among plausible ones.
  • Torch-free: works with both the PyTorch policy and the NumPy one, so the server uses it without torch.
  • Used by the coach, because suggesting the raw DQN argmax would sometimes advise clearly worse discards than the Hard AI plays.

Top 10 interview questions

Q1Why combine a learned policy with a heuristic?
The DQN's Q-values are noisy outside the states it saw often (extrapolation error). Restricting it to the heuristic's top-k makes catastrophic picks impossible while still letting learned preferences reorder good options. It's a form of action-space shaping / safe policy improvement.
Q2Why k = 3?
Large enough that the DQN can disagree meaningfully, small enough that every candidate is reasonable. It was the setting tracked during training evaluations; tuning k was not worth the remaining time.
Q3Why is the hybrid not Hard if it's the RL agent's best form?
Over 4,000 rounds it won 48.2% vs the heuristic's 51.0% self-play baseline: about 3–4 standard errors weaker. Hard is defined as the strongest player.
Q4Why not Medium?
At 48% it's almost as strong as Hard, so the difficulty ladder would have a near-duplicate step. The pure DQN (38%) sits cleanly between Easy (~30%) and Hard.
Q5How does the coach use it?
The coach ranks all legal moves by DQN Q-values (for the preference bars), then bumps the hybrid's choice to first place. The suggestion is therefore near-heuristic strength while the bars still show the network's view.
Q6Is there a risk the hybrid disagrees with the Q-value ranking shown?
Yes; that's why its pick is lifted to the top explicitly instead of trusting argmax Q. The UI shows a preference percentage per move, so a user can see the network's alternatives.
Q7How would you make the hybrid stronger?
Learn k or a confidence threshold (fall back to the heuristic when Q-values are close), or train the DQN only on the heuristic's top-k actions so its Q-estimates are calibrated where it's actually used.
Q8What happens on draws?
Draw and forfeit decisions come from the DQN's masked Q-values over legal actions; draws are a 2–3-way choice, where the DQN's learned behaviour was reasonable.
Q9Does the hybrid ever play an illegal move?
No: candidates come from legal discards and Q-values are masked to legal actions. The server also re-checks every AI move and would fall back to the heuristic, and 50 automated matches recorded zero fallbacks.
Q10How is it tested?
Its win rate is measured in every training evaluation (‘hybrid_vs_heuristic’), in the 20-checkpoint screen and the 4,000-round confirmation; API tests exercise it through the coach.

06 · Training

RLCard environment

rlcard_env.py

What it is

IndianRummyEnv subclasses rlcard.envs.Env and is registered as "indian-rummy". It exposes 56 discrete actions with a legal-action mask, the 1,098-dim observation, raw state for agents that need it, and zero-sum terminal payoffs (opp_points − my_points)/80 clipped to [−1, 1].

Why it's built this way

  • Reuse a maintained toolkit (RLCard, Zha et al., IJCAI 2020) for agents, training loops and conventions instead of writing DQN from scratch.
  • Reveal decisions are auto-resolved by the heuristic reveal policy inside the env, so the RL agent only learns draw / discard / forfeit.
  • Discard by card type (53 ids), not position: the action space is small and permutation-invariant.
  • Training round cap of 120 turns keeps throughput high (real games cap at 300).

Top 10 interview questions

Q1Why RLCard rather than Gym/PettingZoo or a custom loop?
RLCard is built for multi-player card games: it handles turn order, per-player states, legal-action masks and payoffs, and ships DQN/NFSP/DMC agents. Registering a custom env was a small subclass and kept the training code conventional.
Q2How is the action space designed?
0 = closed draw, 1 = open draw, 2–54 = discard a card type, 55 = forfeit. Discarding by type rather than hand position makes the action meaning independent of sorting and keeps the output layer at 56.
Q3How do legal-action masks work with DQN?
The env returns legal actions per state; the agent takes argmax only over legal ones (masking others to −∞), and the TD target maxes over the next state's legal actions. The server re-validates every action anyway.
Q4Why are reveals not RL actions?
Revealing is forced (you must reveal when you have an original) and the only choice is which cards; a solver-based policy handles it well. Removing it shrinks the action space and the credit-assignment problem.
Q5What's the reward?
Sparse terminal payoff scaled to [−1,1]: the point difference / 80, zero-sum, no match multipliers. A forfeit gives exactly −0.5 to the forfeiter, so the agent learns the forfeit trade-off from the reward directly.
Q6How is reward shaping added?
A custom reorganize adds F = γΦ(s′) − Φ(s) to each transition, with Φ = −min_points/80 post-original or a pre-original term based on original outs. Potential-based shaping provably doesn't change the optimal policy (Ng et al., 1999).
Q7Why cap training rounds at 120 turns?
Rare non-terminating rounds (both players stuck) waste simulation time and produce long, low-signal trajectories. The cap is training-only; exhausted rounds are scored normally.
Q8How fast is the environment?
About 2–3 rounds per second in single-process training with the solver in the loop (run C did ~101,600 rounds in 9 h). The solver, not the GPU, was the bottleneck.
Q9How are both seats trained?
In self-play stage B the opponent pool is 50% the current DQN (both seats feed transitions), 30% heuristic, 20% frozen snapshots taken hourly, which reduces non-stationarity and forgetting.
Q10What does raw_obs carry?
The Analysis (solver facts) and legal actions, so the heuristic and hybrid agents can act from the same state RLCard passes, without recomputing the solver.

07 · Training

DQN training

train_dqn.py · DQfD · shaping · CQL

What it is

RLCard's Double-DQN agent (MLP 512-512-256) extended with an O(1) float16 ring buffer, a DQfD large-margin imitation loss on 60k heuristic transitions (6k pretraining steps, then kept during RL with λ decaying 1 → 0.5), potential-based shaping, clipped TD targets, Huber loss and, in the final run, a CQL penalty. Three overnight runs (A, B, C) were evaluated every 5k rounds.

Why it's built this way

  • Pretraining from demonstrations because an untrained DQN plays near-randomly and almost never sees a win in a long sparse-reward round.
  • Run A diverged: mean best-legal Q rose from 0.37 to 4.84 (max 12.4) although true returns are bounded near ±1.5; win rate fell from 37.5% to 14.5%. Diagnosis: overestimation from extrapolation error.
  • Run B (clip targets to ±1.5, Huber, lr 5e-5) slowed the drift; run C added CQL(H) α = 0.5 and was the most stable, but the pure DQN still slid from ~35% to ~25% vs the heuristic.
  • Outcome: the DQfD-pretrained network was the strongest checkpoint of all 20 screened; it ships as Medium (38.3% vs heuristic, 95.8% vs random).

Top 10 interview questions

Q1Why DQN for this problem?
Discrete, small action space (56) with legal masks, an off-policy method that can reuse demonstrations and a replay buffer, and a stable RLCard implementation. Policy-gradient methods (PPO) would need much more on-policy simulation, which the solver-bound env couldn't afford.
Q2What is DQfD and why use it?
Deep Q-learning from Demonstrations (Hester et al., 2018): add a supervised large-margin loss max_a[Q(s,a) + l(a_E,a)] − Q(s,a_E) so the demonstrator's action is at least a margin above others, alongside the TD loss. It gives a competent policy before RL and keeps Q-values grounded.
Q3What went wrong in run A?
Q-values grew far beyond the bounded true return: classic overestimation, amplified because the max in the TD target picks actions the data rarely covers (extrapolation error). The policy chased inflated values and got worse each evaluation; it was stopped at 17.5k rounds.
Q4Why clip TD targets and use Huber loss?
The true return is bounded by the clipped payoff plus shaping (±1.5), so clipping targets removes impossible values; Huber (smooth-L1) limits gradient size from large TD errors. Both are standard stabilisers; they slowed but didn't stop drift.
Q5What is the CQL penalty you added?
Conservative Q-learning (Kumar et al., 2020), CQL(H): add α·(logsumexp_a Q(s,a) − Q(s,a_data)) over the state's legal actions. It pushes down Q on actions not in the data and up on taken actions, directly countering overestimation. The buffer had to store each state's own legal actions for it (RLCard only stores the next state's).
Q6Why did RL fine-tuning still make the policy weaker?
Likely a mix of: the heuristic opponent is near-optimal for its own play style so improvements are subtle; partial observability makes Q(s,a) high-variance; 100k rounds is little for long sparse rounds; self-play non-stationarity; and imitation λ decaying lets TD noise erode the demonstrated behaviour. The honest conclusion was to ship the pretrained network.
Q7How did you decide which checkpoint to ship?
Screen all 20 checkpoints (pure and hybrid) on a fresh seed at 1,000 rounds, then re-test the top candidates at 4,000 rounds on another fresh seed to avoid the winner's curse. The pretrained net won in both.
Q8Why a ring buffer with float16?
RLCard's list buffer pops from the front (O(n)) and stores float64; with 300k transitions × 2 × 1,098 inputs that is ~5 GB. An O(1) ring buffer with float16 halves memory and removes the per-step cost (D-063).
Q9How was exploration handled?
ε-greedy from 0.15 down to 0.03 (low because pretraining already gives a sensible policy), plus opponent diversity from the pool (heuristic, frozen snapshots, self).
Q10What would you try with more time?
Longer DQfD with more demonstrations and a stronger demonstrator, keeping λ high; NFSP or DMC (Deep Monte Carlo, used by DouZero) which suit imperfect-information card games; Monte-Carlo returns instead of bootstrapping; and parallel actors to get 10–100× more rounds.

08 · Training

Value network

train_value.py · calibration

What it is

An MLP (1,098 → 512 → 256 → two heads) predicting P(win this round) (sigmoid, BCE) and the score difference (tanh, MSE) from a player's observation. Trained on 446k states logged during run C, validated on the last 10% in play order, best epoch kept, then temperature-scaled. Held-out ECE 0.020, accuracy 64.4%.

Why it's built this way

  • Separate from the DQN because Q-values mix policy and value and weren't trustworthy as probabilities; the coach needs a calibrated ‘chance to win’.
  • Honest validation split: a random per-state split leaked near-duplicate states from the same round and flattered the metrics; holding out the tail of play order exposed fast overfitting (accuracy 64.4% → 61.4% over 6 epochs).
  • Early stopping on validation BCE kept epoch 0; temperature ended at 1.05 (almost no correction needed).
  • Re-checked under the rule change on 19,000 fresh positions: ECE 0.021, accuracy 65.7%.

Top 10 interview questions

Q1What does calibration mean and why does it matter here?
A model is calibrated if, among positions where it says 70%, the player actually wins about 70%. The coach shows the number to humans; an over-confident model would mislead them even with good accuracy.
Q2How is ECE computed?
Bin predictions into 15 equal-width bins; ECE = Σ_bins (fraction of samples in bin) × |mean predicted − observed win rate|. 0.02 means predictions are off by about 2 percentage points on average.
Q3What is temperature scaling?
Divide the logit by a scalar T fitted on validation data to minimise NLL (Guo et al., 2017). It changes confidence without changing ranking. Here T = 1.05, so the model was already nearly calibrated.
Q4Why was the first version misleading?
With a random split, states from the same round sat in both train and validation, so validation looked fine while the model memorised. With an in-order split it was clear the net overfit after one epoch; the first model only passed the calibration gate because temperature hit the 3.0 grid edge.
Q5Is 64% accuracy good?
For predicting the winner of a card game from a mid-round position with hidden cards and luck, yes; early-round positions are close to coin flips. Calibration matters more than accuracy for a probability display.
Q6How is ‘win chance after a move’ computed?
For discards: the value of the after-state. For the closed draw: average over 16 samples of the hidden cards (the AI's unseen hand and the draw pile are reshuffled consistently with what the human knows). Forfeit is fixed at 40 points.
Q7What data was it trained on, and is there a distribution shift?
States logged from run C's training games (the DQN against its opponent pool: itself, frozen snapshots and the heuristic) after the first 30% of the run. Live games are human vs heuristic/DQN, so there is some shift; the fresh-game check (DQN vs heuristic) and the low ECE suggest it's modest.
Q8Why two heads?
Win probability for the UI; expected score difference was intended for a value-based forfeit rule and as an auxiliary target that regularises the shared trunk.
Q9How would you improve it?
Train on more diverse play (human games, Easy/Hard opponents), add uncertainty (ensembles), condition on the opponent type, and evaluate calibration per game phase (early vs late).
Q10How is it served?
Exported to value_model.npz (weights + temperature), run with NumPy: one batched matrix multiply chain per hint. Verified to match torch to ~1e-7.

09 · Training

Evaluation & selection

evaluate.py · model card

What it is

Fixed-seed head-to-head evaluation with alternating seats and an illegal-move guard; a two-stage checkpoint screen; and the difficulty mapping recorded in models/model_card.json.

Why it's built this way

  • Seats alternate every round because the first player wins ~53% of heuristic self-play rounds.
  • Two-stage screen on fresh seeds: 20 checkpoints × (pure, hybrid) at 1,000 rounds (seed 777), then the leaders at 4,000 rounds (seed 4242), so the final number isn't biased by picking the luckiest run.
  • Standard error at 4,000 rounds is ≈ 0.8 percentage points, so 51.0% vs 48.2% vs 38.3% are clearly separated.
  • Difficulty ladder: Easy ≈ 30%, Medium 38%, Hard 51% (win rate vs the heuristic).

Top 10 interview questions

Q1Why alternate seats?
There's a first-mover advantage (~53% in self-play). Alternating cancels it so a win rate reflects strength, not seat assignment.
Q2What's the standard error of a 4,000-round win rate?
√(p(1−p)/n) ≈ √(0.25/4000) ≈ 0.0079, about 0.8 percentage points. A 3–4 point gap is several SEs; a 1-point gap is within noise.
Q3Why re-test on a new seed?
Selecting the best of many noisy measurements inflates the winner's score (winner's curse / selection bias). Confirming on an independent seed gives an unbiased estimate.
Q4Why is the heuristic's self-play baseline 51% and not 50%?
Finite-sample noise (±0.8) and a shared seed set; it's within about 1.3 SE of 50%. It's the reference point the others are compared against.
Q5Which metrics besides win rate?
Mean score difference per round (captures how badly you lose), forfeit rate, mean turns and an illegal-action count that must be zero.
Q6How was ‘no illegal AI moves’ verified?
Every evaluation wraps agents in an illegal-move guard, and a slow test plays 50 full 7-round matches through the API with a random human; the AI's fallback counter stayed at 0.
Q7Why is Medium the pure DQN rather than the ‘closest to 50%’ rule in the spec?
That rule assumed Hard would be a DQN. With Hard = heuristic it would pick Hard itself or the near-equal hybrid. The pure DQN gives a distinct middle step.
Q8How do you know your model is learning at all?
Gate: DQN beats a random player ≥ 95% of rounds; the shipped net scores 95.8% over 2,000 rounds, and the run logs showed win rate vs random at 85–94% throughout.
Q9What's in the model card?
The level → policy mapping, file paths, provenance (checkpoint, data, calibration numbers) and the evaluation table, so the deployed behaviour is traceable to experiments.
Q10What would a stronger evaluation look like?
Full 7-round matches (variance from ×2 rounds), human play-testing data, Elo across many agents, and confidence intervals reported on the site.

10 · Training

NumPy export & inference

export_models.py · np_models.py

What it is

Converts PyTorch checkpoints into .npz files (weights + a JSON op list: batch-norm, linear, tanh, relu) and runs them with NumPy only. Verified against torch to < 1e-4 (actual 4.5e-6 for the DQN, 1.2e-7 for the value net).

Why it's built this way

  • Torch is ~1 GB; Render's free tier has 512 MB RAM. The NumPy server peaks around 74 MB with 8 games.
  • Tiny models (MLPs) don't need a framework at inference: a few matrix multiplies.
  • Equivalence tested on probe inputs at export time and in tests/test_np_models.py; a feature-version guard rejects stale models.
  • BLAS pinned to one thread in production: with real models, OpenBLAS starting a thread per host core on a 0.1-CPU container made hints take 3.9 s; pinned, ~0.4 s.

Top 10 interview questions

Q1Why not ONNX Runtime or TorchScript?
Both add a runtime dependency and memory; for three dense layers NumPy is enough, easier to audit, and starts instantly. ONNX would be the choice for larger or convolutional models.
Q2How do you reproduce BatchNorm in NumPy?
At inference BatchNorm is an affine transform: (x − running_mean)/√(running_var + eps) · γ + β. The exporter stores those arrays and the op order.
Q3How do you verify the export?
Run both implementations on probe inputs (random and real observations) and assert max |difference| below 1e-4; tests repeat this and check the feature-version guard.
Q4What was the BLAS problem?
NumPy's OpenBLAS starts one worker per visible core. On Render the container sees many host cores but is CPU-quota-limited to 0.1, so threads fought over the quota. Setting OPENBLAS_NUM_THREADS=1 cut hint latency ~10×; locally single-threaded was just as fast.
Q5What is stored in the npz?
Named weight arrays plus a JSON ‘spec’ with the op sequence, feature version, and for the value net the temperature and head shapes.
Q6How is a forward pass done?
Loop over ops: matmul + bias, tanh/relu, BN affine. Batched inputs (2-D) are supported, so the coach evaluates many after-states in one call.
Q7How do you avoid training/serving skew?
Same feature encoder package in both, versioned features, numerical equivalence tests, and the server falls back to the heuristic (logged) if a model fails to load.
Q8How big are the models?
~3.6 MB (DQN) and ~2.6 MB (value) as npz, so they live in the git repo without LFS.
Q9Could the server still use torch locally?
Yes: ai.py loads .pt/.pth with torch if given those paths, which is handy in development; production uses .npz.
Q10What's the latency budget now?
Live on Render: hints ~0.3–0.6 s median, AI moves ~0.2 s; locally hints ~65 ms and actions ~14 ms.

Backend API

FastAPI · sessions · AI players

What it is

A FastAPI app (one Uvicorn worker) holding games in memory: create a game, apply a human action then run AI turns until the human must act, return the new view plus events; hints and explanations; health. Every action is re-validated; illegal ones return 409.

Why it's built this way

  • Server-authoritative: the client is never trusted; legality and hidden information live only on the server.
  • In-memory sessions with per-session locks, 2 h idle expiry and an LRU cap of 500, so one worker is required.
  • Difficulty → policy from model_card.json, with heuristic fallbacks if a model is missing; any illegal model action falls back to the heuristic and is counted.
  • Information-hiding invariants are tested: no response before round end contains the AI's hand, the draw pile, the CJ (before your reveal) or RNG state.

Top 10 interview questions

Q1Why FastAPI?
Async, typed request models with Pydantic, automatic validation and docs, and simple to run with Uvicorn in a small container.
Q2Why only one worker?
Games live in a Python dict in memory. Multiple workers would each have their own dict and requests would hit the wrong one; scaling out would need Redis or sticky sessions.
Q3How do you prevent cheating?
The client sends intents (draw closed, discard card id); the server checks legality against the engine and builds the response from the human's information set only. Tests assert the AI's hand, draw pile and hidden CJ never appear in any payload before round end.
Q4What does one POST /actions do?
Lock the session, apply the human action, then loop AI turns (and automatic transitions) until it's the human's decision or the round ends, collecting events; return the human's view plus those events.
Q5How are concurrent requests on the same game handled?
A per-session asyncio lock serialises them; heavy work runs in a threadpool so the event loop stays responsive.
Q6How is memory bounded?
Sessions expire after 2 h idle via a cleanup task and the least-recently-used are evicted past 500. A game is a few KB; models are shared and loaded once.
Q7What happens if a model fails to load?
The level falls back to a heuristic variant and the health endpoint reports model_loaded: false, so the site keeps working.
Q8How is CORS configured?
Only the GitHub Pages origin (from ALLOWED_ORIGINS) and localhost are allowed.
Q9How was latency measured?
Locally with a TestClient (hint median 65 ms, action 14 ms) and live with a script and Playwright (hint ~0.4 s, action ~0.2 s on 0.1 CPU).
Q10How is the API tested?
Full 7-round matches per difficulty, 409 cases, 404 for unknown games, information-hiding invariants on every payload, LLM fallback, the forfeit-ranking regression, and the 50-match legality test.

Coach & explanations

coach.py · llm.py (Gemini)

What it is

For the human's current decision: win probability now, every legal move ranked (DQN Q-values → preference %, hybrid's pick first), win % after each move from the value net, deterministic reason tags from solver facts, and a template sentence. A separate call asks Gemini to rewrite the facts into ≤ 45 words in the house terminology.

Why it's built this way

  • Grounded explanations: the LLM only sees a facts JSON (moves, win %, tags, rummies, loose cards) and is told not to invent anything; template text is always available.
  • Separate endpoint so the numbers appear instantly and the language arrives when ready (8 s timeout, token bucket 10/min, one in-flight per session, LRU cache by facts hash, replies discarded unless finishReason is STOP).
  • Hidden cards are sampled, not peeked: the closed-draw win % averages 16 resamples of everything the human can't see.
  • House terms (rummy, original/first rummy, secondary rummy, loose cards) are enforced in tags, templates, facts and the prompt.

Top 10 interview questions

Q1How is ‘AI preference %’ computed?
softmax(Q/τ) over legal moves with τ = 0.05, from the DQN's Q-values. A small temperature makes the distribution peaked enough to read but still shows near-ties.
Q2Why put the hybrid's pick first instead of argmax Q?
Against the heuristic the pure DQN wins ~38% and the hybrid ~48%, a 10-point gap. Advising its argmax would sometimes recommend worse moves than the Hard AI plays.
Q3How do you compute win % for a closed draw without cheating?
Determinization: 16 times, shuffle every card the human can't see (AI's unrevealed hand, draw pile, hidden CJ) consistently with known information, apply the draw, evaluate with the value net, and average. The real hidden cards are never used.
Q4How do you stop the LLM from hallucinating?
It receives only computed facts, is instructed to use only those, has a 45-word limit and low output budget, and the UI labels it. Truncated replies are dropped. If anything fails, the deterministic template is shown.
Q5Why Gemini?
Free tier, good speed with the Flash-Lite model, simple REST API. OpenAI was excluded on cost; the code isolates the provider in one module.
Q6What are the reason tags?
Deterministic labels from solver facts, e.g. completes_original, completes_win, reduces_points:n, sheds_high_card, dead_card:n, opponent_may_want, breaks_rummy, discards_wild, outs:n, points_after:n. They drive both the chips in the UI and the template text.
Q7How did you handle terminology complaints?
The user's house terms replaced ‘meld/deadwood’ in tags, template text, facts keys and the system prompt, which now says never to use ‘meld’ or ‘deadwood’. Test replies used the new terms.
Q8What's the latency profile?
Hint (numbers + template) ~0.4 s live; Gemini text typically 1–4 s and swapped in; LLM timeout 8 s because Render (Singapore) calls took ~4.2 s at the old 4 s limit.
Q9Why a regression test for forfeit?
An early version gave Forfeit a flat cost and it topped the ranking; now forfeit is placed just above or below the alternatives based on the heuristic's forfeit rule, and a test checks hints don't push forfeit.
Q10How would you evaluate explanation quality?
Faithfulness checks (every number and card in the text appears in the facts), user studies on helpfulness, and A/B comparisons between template and LLM text.

P1Walk me through the architecture.
A Python rules engine and solver are shared by everything. Because measurement said so: over 4,000 rounds the heuristic beat the hybrid (48.2%) and the DQN (38.3%). The rule ‘Hard = strongest player’ was set before results were known, which avoids moving the goalposts.
P4How do you guarantee the AI doesn't cheat?
The AI's features are built from its own information set; the server re-validates every action and builds each response from the human's information set; tests assert hidden data never appears in payloads; and the coach samples hidden cards instead of reading them.

Theory primer

The background you need to explain and defend the design: imperfect-information games, value-based deep RL and its failure modes, learning from demonstrations, reward shaping, calibrated prediction, combinatorial search and evaluation statistics.

Imperfect-information games

Each player sees only part of the state (their hand, public discards). The right object is the information set: all states consistent with what you know. Policies must condition on it, and planning needs either belief modelling or determinization (sampling hidden cards). Formally it's a POMDP from one player's view.

Q-learning and DQN

Q(s,a) is the expected return after action a. Q-learning moves Q(s,a) toward r + γ·maxa′Q(s′,a′) (Bellman optimality). DQN approximates Q with a neural network and stabilises learning with experience replay (decorrelated minibatches) and a target network (frozen copy for targets). Double DQN selects a′ with the online net but evaluates it with the target net to reduce overestimation.

Overestimation, extrapolation error and CQL

The max in the target picks actions whose values are noisy, biasing Q upward; with off-distribution actions (little data) this compounds. Clipping targets to the reachable range and Huber loss limit damage; Conservative Q-Learning adds α(logsumexpaQ(s,a) − Q(s,adata)) to keep Q low on unsupported actions.

Learning from demonstrations (DQfD)

Pretrain on expert transitions with TD loss plus a large-margin classification loss that makes the expert action's Q at least a margin above others; keep demonstrations in the replay mix during RL. It solves the cold-start problem of sparse rewards.

Reward shaping

Adding F(s,s′) = γΦ(s′) − Φ(s) for any potential Φ leaves optimal policies unchanged (Ng, Harada & Russell 1999) while giving denser feedback. Here Φ is minus normalised points (or an original-outs term before the original).

Self-play and non-stationarity

When the opponent learns too, the environment changes; mixing the current policy, frozen snapshots and a fixed heuristic in an opponent pool reduces cycling and forgetting.

Probabilistic prediction and calibration

A sigmoid output trained with binary cross-entropy estimates P(win). ECE measures calibration by binning predictions; temperature scaling fits one scalar on validation logits to fix over/under-confidence. Validation must be split by game/time, not by state, to avoid leakage.

Combinatorial search

Partitioning a hand into valid groups is a set-partition / exact-cover problem. Precomputed patterns, branching on one card at a time and memoisation over count vectors (dynamic programming) make it fast; a brute-force oracle verifies correctness.

Statistics of evaluation

A win rate over n games has standard error √(p(1−p)/n). Alternate seats to remove first-mover bias, use fixed seeds for paired comparisons, and confirm a selected best model on fresh data to avoid the winner's curse.

Explainable AI

Post-hoc explanation of a policy: expose its scores (Q-values as preferences), an outcome model (win probability), and human-readable reasons derived deterministically from the domain; an LLM is used only to phrase grounded facts.

15 theory questions

T1What is the Bellman optimality equation for Q?
Q*(s,a) = E[r + γ·maxa′ Q*(s′,a′) | s,a]. Q-learning is stochastic approximation toward this fixed point; DQN regresses a network onto the right-hand side computed with a target network.
T2Why does DQN need experience replay and a target network?
Consecutive transitions are highly correlated and the regression target moves with the network; replay samples decorrelated minibatches and reuses data, and the target network holds the bootstrapped target fixed for many steps, which prevents feedback loops.
T3What problem does Double DQN solve?
max over noisy estimates is biased upward (E[max] ≥ max E). Double DQN decouples action selection (online net) from evaluation (target net), reducing that bias.
T4What is extrapolation error?
In off-policy / offline RL, the TD target queries Q at actions poorly covered by the data; the network's guesses there are arbitrary and the max picks the optimistic ones, so errors propagate and inflate values. It's what sank run A.
T5How does CQL counteract it?
It adds a regulariser that minimises a soft-max (logsumexp) of Q over actions while maximising Q on dataset actions, producing a lower bound-ish Q that doesn't favour unsupported actions.
T6Why is potential-based shaping policy-invariant?
The shaping terms telescope along any trajectory to γTΦ(sT) − Φ(s0), a quantity independent of the actions chosen in between (with Φ(terminal) = 0), so the ranking of policies by return is unchanged.
T7What is the DQfD large-margin loss?
JE(Q) = maxa[Q(s,a) + l(aE,a)] − Q(s,aE), where l is a margin (0.8 here) for a ≠ aE. It's zero only when the expert action beats every other by the margin, giving Q-values a grounded ranking.
T8What is an information set and why does it matter for card games?
The set of game states a player can't distinguish given their observations. Policies must be functions of information sets; otherwise they implicitly use hidden cards. The coach also evaluates moves by averaging over states in the human's information set.
T9What is determinization and its weakness?
Sample concrete hidden states consistent with your information and evaluate/plan in each, then average. It's cheap and unbiased for evaluation, but planning with it can suffer ‘strategy fusion’ (assuming you'll know the hidden cards later).
T10Why ε-greedy, and what are alternatives?
Simple exploration: random legal action with probability ε. Alternatives: Boltzmann/softmax exploration, noisy networks, count-based bonuses, or population diversity in opponents.
T11Huber vs MSE loss for TD learning?
Huber is quadratic near zero and linear for large errors, so a few huge TD errors (from bad targets) don't dominate gradients; it's more robust to outliers than MSE.
T12What is Expected Calibration Error?
Partition predictions into bins; ECE = Σb (nb/N)·|acc(b) − conf(b)|. Lower is better; it's the average gap between predicted probability and observed frequency.
T13How does temperature scaling work and why does it not change accuracy?
Replace logit z with z/T and fit T on validation NLL. Dividing by a positive constant preserves the sign of the logit (and the ordering of scores), so the 0.5 threshold decision and ranking don't change, only confidence.
T14How many games do you need to detect a 3-point win-rate difference?
SE of a difference of two independent rates ≈ √(2·0.25/n). For it to be ~1 point (so 3 points ≈ 3 SE), n ≈ 5,000 per agent. Paired/seeded designs reduce the requirement.
T15What makes memoised search efficient for hand arrangement?
Many branch orders lead to the same residual multiset of cards; caching the best result per (residual counts, wilds, slots) turns an exponential tree into a DAG over distinct residual states, which is small because hands are 13–14 cards over 53 types.
